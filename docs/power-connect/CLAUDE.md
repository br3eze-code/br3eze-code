# Power Connect Platform Notes

This document captures the Power Connect implementation context supplied for this repository. It is a companion to the AgentOS instructions, not a replacement for the root `CLAUDE.md`.

## Product and deployables

Power Connect (`africa.br3eze`) is a Wi-Fi hotspot, voucher, and billing platform. The supplied project notes describe these deployables:

| Part | Location | Runtime |
|---|---|---|
| Client PWA and Cordova Android app | `www/` | Browser / Cordova WebView; no bundler |
| Node API | `server/` | Firebase Cloud Function (`server/index.js`) or standalone Node server |
| MikroTik site agent | `server/site-agent.mjs`, setup scripts | Always-on machine on each partner site's LAN |
| PHP/MySQL portal | `www/index.php`, `www/php/` | Separate PHP 8.2+ host; excluded from Firebase Hosting |
| Custom Cordova plugins | `custom-plugins/` | Native Android/iOS code plus JavaScript bridges |
| Firebase configuration | Firestore/Storage rules, indexes, Data Connect | Firebase |

These details describe the supplied Power Connect source notes. Verify them against the current checkout before changing implementation or deployment.

## Ownership and boundaries

- **AgentOS execution ownership:** AgentOS's canonical runtime owns agent execution and orchestration. Power Connect-specific behavior should be exposed through explicit adapters, skills, or tools rather than creating a competing general-purpose runtime.
- **Client source:** edit `www/`, not generated Cordova copies under `platforms/`.
- **Cordova lifecycle:** the supplied notes assign `www/js/index.js` ownership of `deviceready`, back-button handling, notification taps, and the native bridge. Feature code should call the shared `Device`, `NetworkTools`, or `NativeApp` abstractions instead of native APIs directly.
- **Device capability decisions:** `Device.platformInfo()` and `Device.permissions` are described as the central owners of platform rules and permission decisions. Avoid parallel user-agent/platform branches and direct permission-plugin calls in feature code.
- **Client module registry:** `www/js/registry.js` is generated by `npm run modules:registry`; update script loading first, then regenerate the registry.
- **Routing:** `firebase.json` is the route configuration authority; `scripts/dev-server.mjs` mirrors its file-first, rewrites, then 404 behavior.
- **Router access:** the app/API should not connect directly to partner MikroTik routers. A site agent on the partner LAN polls the API over HTTPS and communicates with RouterOS on the LAN.
- **Money movement:** clients must not write balances or ledger entries. Payment verification uses provider-confirmed amounts/references and server-side transactional handling.
- **Credentials:** never place secrets in browser-visible environment output or native source. The supplied notes warn that local development may use production Firestore if `serviceAccountKey.json` is present; announce and verify this before running it.

## Local development and verification

The supplied notes identify these commands; check the current `package.json` before relying on them:

- `npm run dev`: local web app and API, with the app served at `127.0.0.1:5050`, API at port `3000`, and `/api/**` proxied to the API.
- `npm run start:local`: production-mode local serving on port `8080`.
- `npm test`: root Node test suite.
- `npm run env:www`: regenerate the public client environment file from the explicit allow-list.
- `npm run build:android:aab` / `npm run build:android:apk`: Android packaging.
- `npm run build:electron`: Electron desktop packaging.
- `npm run test:rules`: Firestore rules emulator tests.
- `node custom-plugins/wbs-agents/smoke-test.mjs`: plugin governance smoke test.
- From `server/`, `npm start` starts the standalone HTTP/WebSocket gateway; `npm run lint` is described as syntax checking only.

## Wi-Fi provisioning and native compatibility

The supplied notes describe `www/js/wifi-provision.js` as the provisioning entry point, used by `NetworkTools.connectToWifi`. Native outcomes should be structured results such as `{ ok, code }`; unsupported capabilities must report an explicit unsupported result rather than hanging or pretending success. Browser fallback uses a Wi-Fi QR/password flow. Do not use `WifiNetworkSpecifier` as a general internet-network solution.

After changing native plugin Java, reinstall the local plugin so Cordova copies the new implementation into the platform build. Android SDK gates should use capability floors/fallbacks rather than exact SDK equality checks. Native services/listeners require explicit shutdown paths and per-operation permissions.

## Router/site-agent security

- Keep RouterOS commands behind a narrow allow-list; the supplied notes name health checks, creation of a single hotspot voucher/user, and disabling a hotspot user.
- Require site approval/active status for write actions, use short-lived commands/leases, and expire queued commands.
- Enrollment tokens are one-time; store only hashes and rotate tokens on re-enrollment.
- Do not disable TLS verification or expose arbitrary RouterOS command execution.
- Keep billing/voucher policy above the generic network layer.

## Authentication, payments, and data

- Roles are assigned through server-controlled onboarding/admin approval, not self-assigned by clients.
- Server-side transactions own credit balances, voucher redemption, plan purchases, shop orders, and peer-to-peer credit transfers.
- Payment amounts and references must come from trusted provider responses, not request-body claims.
- Webhook signature checks must use the provider's required raw request body and secret.
- Do not cache `/api/` or credentialed requests in the service worker.
- The supplied notes identify an unresolved sign-in risk: an owner-writable `phoneNumberE164` value may interfere with phone sign-in for numbers that Firebase has not verified. Check `OPEN_ITEMS.md` before assuming it is resolved.
- The PHP portal is a parallel entry point with MySQL data that is not synchronized with Firestore; do not assume shared persistence.

## Required engineering approach

1. Inspect the actual live entry point and import/call path before editing; the supplied notes explicitly warn that some scripts and directories may be leftovers from other projects.
2. Preserve one accountable owner per concern. Prefer thin compatibility wrappers and adapters over duplicate orchestration, gateway, device, or billing owners.
3. Treat the supplied notes as historical context, not proof of current behavior. Confirm files, scripts, deployment settings, tests, and unresolved items in the current branch.
4. Add or update regression tests when changing routing, native result codes, permission behavior, Firestore rules, payments, or router command validation.
5. Do not claim platform compatibility without a reproducible build/test artifact.
