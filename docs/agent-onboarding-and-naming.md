# Agent identity, naming and onboarding

## Identity is not the same as a specialist role

Br3eze has three separate concepts:

1. **Role profile** — a reusable definition of responsibilities, capability hints and approval-sensitive actions.
2. **Agent identity** — one persistent, tenant-owned agent instance with its own immutable database UUID and lifecycle state.
3. **Effective policy** — the active, persisted tenant policy that actually authorizes tools and resource scopes.

A role name is not a permission. The capabilities stored with an identity are profile metadata; runtime authorization must read the active `agent_policies` record and verify the current tenant membership.

`AgentRegistry` is an in-memory registry of role/specialist definitions. It is not the persistent store for multiple agent instances. Persistent identities use the tenant-scoped registry and Supabase identity-store adapter.

## Canonical naming contract

`agent.create` accepts a small, non-authoritative definition:

```json
{
  "name": "Field Engineer",
  "role": "engineer",
  "domain": "network",
  "agentType": "assistant",
  "purpose": "Inspect network health and prepare bounded changes."
}
```

The system derives:

- `id`: immutable UUID generated by the database.
- `agentKey`: tenant-unique machine key, e.g. `engineer:field-engineer`.
- `name`: human-readable display name.
- `role`: normalized role-profile key.
- `tenantId`, `createdBy`, `ownerUserId`: derived from the authenticated server context, never trusted from the request body.
- `status`: `pending` until a separate policy/activation step succeeds.

The request cannot supply its own ID, key, capabilities, permissions, tools, parent identity or resource scopes. A role profile can provide safe defaults, but cannot activate the agent or grant effective authority.

## Supported role profiles

Canonical roles include:

- General: `planner`, `engineer`, `accountant`, `secretary`, `procurement`, `expeditor`, `designer`, `draftsman`, `qa`.
- Commerce: `catalog`, `pricing-promotions`, `inventory`, `orders-checkout`, `voucher-access`, `billing-payments`, `product`.
- Delivery: `project-manager`.
- Br3eze onboarding: `br3eze-code` (alias for the Br3eze Service Agent profile).

Aliases include `fulfillment-expeditor` → `expeditor`, `catalog-specialist` → `catalog`, `billing-payments-specialist` → `billingpayments`, and `br3eze-code` → `br3ezeserviceagent`.

## Persistent onboarding sequence

1. A human signs in through Supabase Auth.
2. The server verifies the access token and derives the user ID.
3. A server-only onboarding service creates the tenant and owner membership atomically.
4. An authorized owner creates an agent identity; the identity is stored as `pending`.
5. A separate, persisted approval/policy step grants exact capabilities and resource scopes.
6. The server issues a short-lived agent credential and activates the identity.
7. Every tool call rechecks agent status, tenant membership, credential validity, policy and resource scope.

Never create the first tenant or owner membership from a client-supplied user ID. The identity tables intentionally have no client write policies; onboarding writes must happen in a trusted server adapter.

## Current implementation status (2 November 2026)

- The Supabase project `br3eze-code` has the tenant and agent identity migrations applied.
- The seven agent identity tables exist with RLS enabled and security advisors returned no findings.
- Live counts at inspection: **0 Auth users, 0 tenants, 0 memberships and 0 agent identities**. The database is structurally ready but has no initial human owner or tenant to onboard.
- The provider-neutral lifecycle port, tenant-scoped registry and Supabase identity-store adapter now exist.
- The lifecycle port forwards authenticated context into the tenant-scoped registry and validates role/name creation.
- The lifecycle port is **not yet wired to a public API route or CLI command**. The production authorizer, persisted approval flow, tenant bootstrap endpoint and credential issuance must be composed before enabling execution.
- `agentos onboard` currently configures a local AgentOS profile; it does not create a Supabase tenant or persistent agent identity.

Do not describe agent provisioning or autonomous execution as production-ready until the server composition and end-to-end tenant-isolation tests pass.
